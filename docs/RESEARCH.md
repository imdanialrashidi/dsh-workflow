# Evidence behind the workflow

Reviewed on 2026-11-22. This is a targeted review of primary research, maintainers' evaluations, standards and operating guidance. The design question was which changes would catch an incorrect delivery, without making an ordinary fix expensive. The starting point was Git revision `93c9281`. Its 152 local repository checks passed. They exercised the pack and its installer. They did not measure a model's success on a customer's project.

## What the evidence changes

| Evidence | Scope and limitation | Decision for this pack |
| --- | --- | --- |
| Context files increased inference cost by over 20% on average across the study settings and did not generally improve success. The authors found value in nonstandard project instructions. [Gloaguen et al., 2026, revised paper](https://arxiv.org/abs/2602.11988) | Tested agents, tasks and repositories. No universal context-size optimum follows. | Keep the global routing file small. Put project-owned commands in one place. Load test, review and release detail on demand. |
| Four maintainers from three repositories evaluated 296 AI patches. Roughly half of test-passing patches would still have received a request for changes. [METR, March 2026](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/) | Older agents and a hypothetical merge decision without the normal repair conversation. | Judge acceptance, integration with callers and maintainability. Record reviewer identity or role separately from test results. |
| An audit found tests rejecting correct alternatives and evidence of contamination. A subsequent audit withdrew the team's earlier recommendation to switch to SWE-Bench Pro. [February audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/) · [July follow-up](https://openai.com/index/separating-signal-from-noise-coding-evaluations/) | Benchmark-specific investigations by a model developer. A private acceptance suite can also encode an implementation preference. | Freeze expected outcomes before coding and inspect the grader. Accept equivalent correct implementations. Keep pilot holdouts outside the writer's workspace. |
| An observational preprint covered 114,134 merged PRs across 391 Java repositories. Similar overall test-edit rates masked within-project differences. Test-quality conclusions were uncertain. [Milanese et al., October 2026](https://arxiv.org/abs/2610.35297) | Java, merged changes, inferred agent involvement. Counts and coverage alone cannot establish the value of a test. | Require a plausible wrong outcome the assertion distinguishes. Evaluate both workflow versions within the same project and risk tier. |
| A preprint compared 1,130 agent and 1,130 human performance PRs. About half of validated PRs across the two groups lacked a quantitative performance metric. [Peng et al., October 2026](https://arxiv.org/abs/2610.03969) | Describes reported validation. It cannot tell whether unreported experiments occurred. | For a speed or resource claim, use matched workloads and environments, repeated measurements and a relevant cost such as memory. Mark the claim unproven when measurement is missing. |
| Agent evaluation benefits from multiple trials, checks on the resulting state and periodic calibration of graders against human judgment. [Anthropic, January 2026](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) | Practitioner experience with specific harnesses. An evaluator model can share the writer's blind spots. | Keep deterministic checks and a separate owner judgment. Record failed and blocked trials and the cost of retries. |
| NIST's SSDF describes preparation, software protection, secure production and response to vulnerabilities. The publication list identifies 1.1 as final and 1.2 as a draft. [SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final) · [publication status](https://csrc.nist.gov/projects/ssdf/publications) | Lifecycle guidance. | OWASP ASVS 5.0.0 provides versioned, testable web application requirements. OWASP also documents agent tool permissions, trust boundaries and scoped execution. [ASVS](https://asvs.owasp.org/) · [Secure Coding with AI](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Coding_with_AI_Cheat_Sheet.html) · [Securing Agentic Applications V2, November 2026](https://genai.owasp.org/resource/securing-agentic-applications-v2/) | ASVS concerns web applications. Agent guidance addresses both the model and the software that grants access to tools. | Link an applicable control to a denial test. Review changed skills, scripts and hooks before execution. Scope credentials, tools and data by environment using platform controls. |
| GitHub recommends pinning actions to full commit SHAs and restricting token privileges. [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use) | Applies to GitHub Actions. A pin identifies content but does not establish that its author or behavior is trustworthy. | Keep CI read-only, verify third-party action references, and inspect changes to the checks themselves. |
| SLSA describes verifying a signed attestation against trusted identities, the artifact digest and expected build inputs. [SLSA v1.2 verification](https://slsa.dev/spec/v1.2/verifying-artifacts) | Relevant to a release pipeline that produces and verifies provenance. A checksum alone cannot authenticate a builder. | For a distributed artifact, identify exactly what was verified and by whom. | A canary needs a meaningful comparison, a decision signal and a recovery route. [Google SRE Workbook](https://sre.google/workbook/canarying-releases/) | Applies to deployable services. | DORA measures delivery speed together with instability at application or service level. [DORA metrics guide](https://dora.dev/guides/dora-metrics/) | Production outcomes also depend on the team, platform and release mix. | Track downstream failures and rework alongside time to an accepted change. ## Where the original pack fell short

| Observed at the starting revision | Changed entry point | Evidence a team can inspect |
| --- | --- | --- |
| Quality policy permitted completion when an unmet criterion was disclosed. The verify report had no explicit decision rule. | Global instructions, verify, review and project quality template | A failed required criterion yields a negative verdict. A missing required observation leaves verification incomplete. |
| The project template repeated command placeholders in two files. A stale entry could compete with the current CI configuration. | Project entry point and quality template | One command table with a pointer to the version-controlled command definition. |
| A verifier could report a successful exit without noticing that the acceptance test was filtered out. Performance claims had no comparison protocol. | Verify and test-design | Selected case actually ran, observable result, same-workload before/after for a performance claim. |
| High-risk guidance asked for rollback and review but did not describe evidence for releasing a particular artifact or recovering an irreversible migration. | Build, review, project quality template | Revision, artifact identity, signal, recovery rehearsal or evidence gap, and accountable owner. |
| DSH lets a project shadow a global skill. The installed baseline did not explain the trust implications. Install and scaffold also trusted child directory links. | Global instructions, security policy, install and init | Inspect a changed instruction source before execution. Isolated path-safety checks cover both write entry points. |

## Evaluate adoption on customer work

1. Pick recent, representative tasks from one service. Include a localized bug, a normal feature, a sensitive change and an environment-blocked task. Use sanitized snapshots and reserve several tasks for the final evaluation. Freeze base revision, acceptance cases and what counts as a blocker before generating patches.
2. Run the old and new packs in fresh, isolated sessions on each snapshot. Hold model version, tool permissions, runtime, dependency lock and time budget constant. Vary run order. Where the budget permits, repeat each arm with fresh sessions and report the number of trials.
3. Give a maintainer the same task, final diff and evidence for each candidate, with pack identity hidden where practical. Keep the reference implementation and private fixtures with the evaluator. Score functional acceptance and security invariants independently. Record an incorrect grader or ambiguous task separately and re-score both arms after a documented correction.
4. Record counts and denominators for accepted changes, required checks actually executed, false-ready claims, and introduced regressions. Record elapsed time to accepted change, reviewer minutes, repair rounds and model cost when available. Include timeouts and blocked runs in totals. Show paired differences and disagreement cases. Small samples justify inspection of individual cases before broad conclusions.
5. Agree on a rollout rule with the service owner before seeing the results. An example rule pauses adoption for any new false-ready decision on a sensitive task. Review cost and acceptance together, then expand by service if the trade-off is acceptable. After release, review escaped defects and rework over the team's normal reporting window. An escaped defect becomes a candidate private regression case.

| Pilot task | Observable acceptance | What disqualifies a “ready” result |
| --- | --- | --- |
| Fix formatting of a value in an existing export | A real export fixture has the requested field and unchanged adjacent fields | Only a formatter unit test ran, while the actual entry point still uses a different formatter |
| Include tenant-filtered records in an export | Permitted actor receives its own seeded records. Denied actor obtains no file or queued export | Only the HTTP status was asserted, or a second tenant's seeded row appears |
| Migrate a stored value in batches | Old and new consumers can read the transition. Restarting a partially completed batch preserves the agreed state | A rerun duplicates records or the recovery path lacks required evidence |
| Verify a feature when its staging dependency is unavailable | Independent local checks run, and the required staging observation stays blocked | The report substitutes a mock result for the missing integration evidence |

Use one row per trial in the team's existing tracker: task, risk tier, base, pack, model, trial, required cases passed/total, maintainer verdict, false-ready, elapsed/reviewer minutes, cost and reason for any gap. Results from the repository's tests and DSH headless integration checks are reported separately from customer acceptance rates.

## Local validation before adding the production skill

The shell suite ran in isolated Linux directories. It reported 152 checks at the starting revision and 177 after the changes, all passing. The count includes document and configuration checks as well as filesystem tests. Added behavioral checks exercise root resolution, managed directory boundaries, lock contention and non-overwrite behavior.

The optional DSH integration test passed against `0.2.1-rc.2` and `0.2.2-rc.5` on Linux with Node 24.22.3. The real headless CLI delivered both instruction files, the six-entry catalog and the complete explicitly invoked verify skill to a local responder. The responder returned a fixed answer. No external model judged a project. See the [capability map](DSH-CAPABILITY-MAP.md) for the scope and reproduction command.

The global entry point fell from 3,406 to 2,281 bytes, and the initialized project entry point from 2,748 to 1,404 bytes. These are UTF-8 file sizes. Inference cost, defects after release and time saved remain measurements for the paired pilot.

An independent code review covered the installer, initializer and verdict rules. The final Linux checks included competing writers and preservation of a symlink backup. Hosted CI was pending at this stage. On 2026-11-23, after the production skill was added, the Ubuntu and macOS jobs each reported 188 checks and zero failures. [GitHub Actions run 45136810552](https://github.com/imdanialrashidi/dsh-workflow/actions/runs/45136810552)

## Evidence behind the production skill

Reviewed on 2026-11-22. The question was what a maintainer should ask an agent to demonstrate before handing a particular release to an operator. The following evidence informs the selection of checks in [the production skill](../skills/production/SKILL.md). Numerical thresholds belong to the workload and its owners.

| Evidence and scope | Decision reflected in the skill |
| --- | --- |
| Google's production readiness process starts from the reliability needs of the particular service. Its SLO guidance connects user-visible good events, agreed targets and an observation window. [Readiness reviews](https://sre.google/sre-book/evolving-sre-engagement-model/) · [Implementing SLOs](https://sre.google/workbook/implementing-slos/) · [Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/) | Begin with a critical journey and a failure the operator can detect. Separate relevant gates for a service, worker, UI and distributed package. |
| Yuan et al. studied 198 user-reported failures in five distributed data systems. Input sequences and their ordering mattered. This historical sample provides a test-design pattern, with limited generalizability across workloads. [USENIX OSDI paper](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/yuan) | Exercise a concrete sequence such as commit, timeout, retry and restart. Inspect the final persistent effect. |
| In GitHub's October 2026 report, reconnections amplified pressure and the audit-event pipeline needed additional time to catch up. AWS documents how retries can amplify load and how queues accumulate work faster than it can be completed. [GitHub incident report](https://github.blog/news-insights/company-news/github-availability-report-october-2026/) · [Timeouts and retries](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) · [Queue backlogs](https://aws.amazon.com/builders-library/avoiding-insurmountable-queue-backlogs/) | Check concurrency, retry budgets, oldest outstanding work, processing of new arrivals during recovery and the final user-visible result. |
| Cloudflare traced its November 2025 outage to a generated configuration file that grew beyond a consumer's limit and propagated across the network. Its postmortem describes the interaction of mixed versions and configuration generation in that incident. [Cloudflare postmortem](https://blog.cloudflare.com/18-november-2025-outage/) | Include generated configuration in the candidate. Check consumer limits and behavior when an update is rejected. |
| AWS describes compatibility at intermediate versions of a rollout and checking actual restoration against recovery time and data-loss objectives. Google SRE describes comparing a limited canary with a control. [Rollback safety](https://aws.amazon.com/builders-library/ensuring-rollback-safety-during-deployments/) · [Restore testing](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_backing_up_data_periodic_recovery_testing_data.html) · [Canarying releases](https://sre.google/workbook/canarying-releases/) | Test mixed-version reads/writes and rehearse recovery appropriate to the data change. Tie promotion or stopping to a window, comparison population and customer outcome. |
| OWASP defines testable web security requirements and describes secret lifecycle controls. OpenTelemetry documents data minimization and redaction, while SLSA specifies artifact verification against a trusted builder and expected inputs. [OWASP ASVS](https://asvs.owasp.org/) · [Secret management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) · [Telemetry privacy](https://opentelemetry.io/docs/security/handling-sensitive-data/) · [SLSA artifact verification](https://slsa.dev/spec/v1.2/verifying-artifacts) | Exercise authorization through the last side effect, inspect sanitized signals and identify the exact artifact tested. Use security or provenance gates mandated by the project's policy. |
| NIST's final incident response guidance integrates preparation, response and recovery. The Kubernetes project documents distinct routing and restart probe semantics. [NIST SP 800-61 Rev. 3](https://csrc.nist.gov/pubs/sp/800/61/r3/final) · [Kubernetes probe semantics](https://kubernetes.io/docs/concepts/workloads/pods/probes/) | Identify the person who can act on a signal, the recovery path and the escalation contact. For an orchestrated service, distinguish losing traffic from restarting the process. |
| WCAG 2.2 defines testable accessibility criteria for web content. The FinOps Foundation describes unit costs tied to outcomes such as a transaction or customer served. [WCAG 2.2](https://www.w3.org/TR/WCAG22/) · [FinOps unit economics](https://www.finops.org/framework/capabilities/unit-economics/) | Exercise the affected user journey and its applicable accessibility requirements. For a cost-sensitive workload, compare cost per completed unit and user-visible performance under matched load. |

The incident reports describe individual systems. The standards and operating guides offer engineering practices. The resulting readiness verdict covers the selected candidate, checks and environment. It cannot establish certification or predict an incident rate.

With the production skill installed, the isolated shell suite reported 188 checks and zero failures. On Linux, the DSH compatibility test loaded all seven skill bodies in both supported versions. Separate headless sessions delivered the complete explicitly invoked `/production` and `/verify` bodies to a loopback responder. This checks installation and routing. Production outcomes and live-model decisions require project-specific evaluation.

### Calibrating the production verdict

These are worked examples for the release owner. Each row states the facts assumed for the example.

| Candidate evidence | Expected verdict | What to hand off |
| --- | --- | --- |
| An isolated retry creates a second ledger charge. The required recovery drill is also missing. | Changes required | Cite the duplicate charge as the demonstrated failure. Fix the retry behavior, rerun the same sequence, and retain the missing drill as an additional gap. |
| The stateful release passes its functional checks. A required restore exercise has no result for the relevant data format. | Blocked | Name the recovery owner and the isolated restore needed to measure integrity, data loss and elapsed time. |
| A stateless library passes all agreed consumer, packaging and compatibility checks on the same artifact. Required reviews are recorded, no risks remain open, and permission to publish is pending. | Ready | Give the owner the verified artifact identity and evidence. Record pending publication authorization and wait for the owner's release decision. |

An isolated upgrade from the previous six skills added only the production skill while preserving a customized global instruction file. The installer returned its documented conflict status for the global file. A second installation also preserved an existing customized production skill.

### Executed ledger exercise

On 2026-11-23 we exercised the readiness rules on a synthetic SQLite ledger using `python3 tests/production-cases.py`. The two release requirements were one persisted row per logical request and recovery of the two agreed rows through the normal statement reader within 30 seconds of starting the isolated restore. Writes were quiesced at a known cutoff. The timing target belongs only to the fixture. The release policy in this exercise requires no additional sign-off for technical assessment. Deployment authorization is pending throughout.

| Case | Executed observation | Decision under the skill |
| --- | --- | --- |
| A | The first process committed 1,250 cents and exited before acknowledging. A fresh process retried and recorded another 1,250 cents for the same ID. A different 340-cent request was recorded once. No restore exercise ran. | **Changes required**. The duplicated effect is a demonstrated failure. The missing restore remains a second gap. |
| B | With the corrected write logic the statement showed exactly 1,250 and 340 cents. A database backup was created. There was no read from a restored copy. | **Blocked**. The retry check passed. The release owner still needs restore evidence. |
| C | The worker and write logic were byte-identical to B. The backup was restored to a fresh database. A new consumer process read both expected rows within the fixture limit. | **Ready** for the two fixture gates. Publication remains pending. |
| D | The same candidate restored a structurally sound older backup. SQLite reported `ok` for the integrity check. The normal consumer returned only the 1,250-cent request. The 340-cent request acknowledged before the required cutoff was absent. | **Changes required**. The restore ran and demonstrably missed the required recovery point. |

The runner prints the candidate digest, observed rows, check statuses and recovery time. Its exit code indicates whether the exercise produced its expected observations, including the deliberately failing first candidate. The verdicts in the table are our application of the written skill. The exercise used local storage and synthetic charges. It did not exercise an external payment service, a customer deployment or live DSH model inference.
